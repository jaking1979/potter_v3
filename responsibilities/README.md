# responsibilities (package E2, decision T16)

A responsibility is a standing duty, such as a morning brief, bill watch or follow-up. This package runs them on top of C1 (`policy/`), C2 (`runtime/` tasks and effect journal) and E1 (`notifier/`). It is staging-only (T22): connectors are injected, and the only ones in this repository are offline test fakes.

```
trigger ─(C2 trigger key)─▶ task ─claim─▶ reconcile gate ─▶ step: C1 decide ─▶ C2 record_intent/execute ─▶ connector
                                                               │ deny(needs approval)
                                                               └▶ E1 ApprovalIssuer ─▶ waiting_approval ─/approve─▶ queued
results · long-work state · escalations · watchdog ─▶ E1 JobHandle (enqueue-only) ─▶ C3 outbox
```

| Module | What it does |
| --- | --- |
| `definitions.py` | `Responsibility(id, trigger, delivery, steps, cadence_s, …)`. The trigger is `Schedule(every_s)` or `Event(topic, key fields)`. Delivery is `"josh"` or `"silent"`. Each `Step` names a C1 capability, its bound action (static, or a deterministic builder over the payload and earlier results) and a connector identity. |
| `runner.py` | `ResponsibilityRunner`: `tick`, `on_event`, `run_once` / `run_pending`, `poll_approvals`, `live_action` (for E1's `CommandRouter`), `watchdog` and `recover`. |
| `_schema.py` | `responsibility_state` (schedule watermarks), `responsibility_approvals` (the one E1 request claimed per task and action), `responsibility_holds` (tasks awaiting an operator after an upgrade), `responsibility_finals` (completed tasks whose long-work final is still owed) and `responsibility_progress` (long-work start time). Pinned by `meta.responsibilities_schema=e2.v3`; `e2.v0`/`e2.v1`/`e2.v2` upgrade in place, in one transaction. Legacy approvals are reconciled (from v0/v1), and tasks that had already failed or escalated are recorded as delivered, so an upgrade never re-announces history. |

## How each requirement is met

1. **Dedupe.** Trigger keys are `resp:<id>:slot:<n>` for schedules and `resp:<id>:event:<subject>` for events. The subject is the typed canonical JSON of the `[field, value]` pairs (values must be non-empty strings or integers), so values containing separators, or `1` versus `"1"`, never collide. They go into C2's unique trigger key, so a duplicate trigger, even from another process, returns the existing task. Event keys come from subject fields, never from arrival order, so a reordered or late copy also maps to the same task (the first payload is kept). A schedule tick for a slot older than the watermark is dropped. The watermark check, its update and the task insert are **one** write transaction (C2 `submit(..., tx=)`), so concurrent ticks serialize and a tick that decided on an old watermark can never insert after a newer tick moved it. There is no state between the two: a crash before commit records neither, and the next tick submits its own current slot. If that tick is already in a later slot, the missed one is skipped, per the late-slot rule.
2. **Steps go through C1, then C2.**
   - `allow`: `record_intent(task, step, action)`, then `execute(..., connector=)`.
   - A deny whose only reason is a missing approval (`approval_required` / `untrusted_context_requires_approval`): the runner checkpoints the action's hash, moves the task to `waiting_approval`, and only then makes one request through E1's `ApprovalIssuer`, because E1 issues requests only for a waiting task. The approval is found later by task and action hash. If a crash or the kill flag hits between parking and requesting, the task waits with no request, and `poll_approvals` issues it (after the flag clears). Find-or-create is one `BEGIN IMMEDIATE` transaction: the claim lookup, E1's `ApprovalIssuer.request(tx, …)` and an insert into E2's `responsibility_approvals`, whose primary key is (task, action hash), commit together. Overlapping workers or processes therefore serialize, and exactly one request exists per action, so Josh is never prompted twice. A claimed request that ends denied, expired, voided or cancelled is never re-issued: the run fails.
   - Any other deny fails the run.
   - Event triggers always carry untrusted provenance (`external_event`), so any write they cause needs an approval. Reads do not. A definition's `provenance` can add sources to an event but never remove `external_event`.
   - **Result provenance.** A trusted schedule does not authenticate the data a step reads. Each step declares `result_provenance`. If it is undeclared, the result counts as `unverified_result`, which is untrusted. A result mapping's own `"provenance"` list is added to that declaration, and can only add sources. Any later step whose action is built by a callable (so it may use earlier results) sends C1 the union of the trigger's provenance and every earlier result's provenance. A write derived from mail, web or document content therefore needs an approval, including across intermediate steps and restarts. Steps with static parameters are not affected.
3. **Never sends.** The runner holds only `JobHandle`s. Each responsibility gets one bound to its declared delivery. A `potter.ops` handle (always `josh`) carries escalations and watchdog alerts, so a silent job's failures still reach Josh. `notifier.lint` passes over this package.
4. **Kill flag (E1).** It is checked before a claim, before every step and right before every dispatch, and `tick` does nothing while it is set. A call already in flight completes and C2 records it. Nothing after it runs. The checkpoint `{"next": i, "interrupted": true}` records where to resume. Once the operator clears the flag, the run resumes at step `i`, and completed steps are skipped from the journal. The check right before a dispatch is one marked seam, `_dispatch_permitted()`. If the kill flag stops the result message, the task is not completed: it is interrupted at `len(steps)` and delivers the result once the flag is cleared, without re-running any step.
5. **Recovery.** Leases are C2's: a dead worker's task is reclaimed when its lease expires. Before any step of a claimed task runs, each of its `unknown` effects is reconciled through `EffectJournal.reconcile`, which never dispatches. If an effect stays unknown or in flight, the task is **blocked**: a retryable failure, which C2 escalates after 3. Re-dispatch happens only where C2 allows it (a fence, or a trusted contract digest). An approved step whose nonce was consumed before a crash resumes through C1's `retry_intent` path (`reconcile` outcome) and then C2.
6. **Long work (T16 states → E1 `LongWork`).** States are `queued`, `running`, `waiting_approval`, `done`, `failed` and `escalated`. The run's start time is persisted on the first report, so the 30 s clock survives a restart. That start time is the only thing E2 stores. **E1's durable outbox is the only record of what Josh was told:** every report ticks E1's `LongWork`, which reads its progress back from the outbox and treats a repeated tick as a no-op. So a crash between pinning the start and E1's enqueue is retried by the next report, never mistaken for a sent ack. **Success is never announced before C2 records it:** `_finish` commits the job result message, C2's terminal `complete(..., tx=)` (lease-checked) and a pending `responsibility_finals` row in ONE transaction. A crash, lease loss or kill before that commit leaves none of them, and the run is redone (no step repeats) or interrupted. The long-work "done" update and final message, which E1 writes in its own transactions, go out only after the commit; `deliver_pending_finals()` (run by `report_progress()` and `watchdog()`) re-sends them idempotently if a crash lands in between. A final is marked delivered only on durable proof: nothing was owed (a short or silent run, decided at completion), or E1's outbox holds the task's `work:<job>:<task>:final` row. Any notifier failure, such as a missing recipient address or the kill flag, leaves it pending for the next sweep, and so does a final whose responsibility definition is not loaded. A `NotifierError` is never read as "already finished" on its own. **Terminal failures are durable too:** after C2 commits FAILED or ESCALATED (from `_fatal`, a terminal retry, a rejected or expired approval, or C2's own escalation of a repeatedly reclaimed task inside `claim`), the owed messages are recorded in `responsibility_finals` and delivered with the same proof rule: the long-work final with its outcome and receipt, and for FAILED the failure alert with its receipt. C2's terminal state is the durable record, so a crash between that commit and the record is recovered by `deliver_pending_finals()`, which backfills a finals row for every FAILED or ESCALATED responsibility task without one. Whether a final is owed is judged from C2's committed terminal timestamp (`tasks.updated_at`, read in the same transaction for DONE, and by the record or the backfill for FAILED/ESCALATED), never from when the record happens to be written. Nothing is announced before the terminal commit. ESCALATED is announced through the ops job's escalation sweep. Whether a run gets the final long-work message depends on elapsed time (30 s or more since its first report), not on local history. `poll_approvals` ticks still-pending waiting tasks, and `report_progress()` (called periodically by the C8 loop) ticks every running and waiting task, so the 30 s ack arrives even during one long step or a long-pending approval. The result is an ack after 30 s, an update only on a state change, and a final message with `potter://receipts/<task_id>`. Short successful runs send just the `job_result` (with the receipt) when the definition declares a `report`.
7. **Watchdog and escalation.** `watchdog()` alerts on C2 `stale_jobs` (cadence × tolerance), with one alert per bucket. It also re-enqueues every escalation idempotently, because C2's escalate callback is at-most-once after commit.

## Known gaps / decisions for review

- **Kill check to dispatch is not atomic.** `_dispatch_permitted()` reads E1's kill flag, and C2 `execute` claims the effect in a separate transaction. A `/stop` that commits between the two can still be followed by one dispatch. This is the same window found in E1 #28. E1 (`1b88a01`) closed it for notifier sends with a private gate that `stop()` waits on, but that gate does not fence responsibility connector effects, and E2 must not reach into it. Candidate follow-ups, to be wired into `_dispatch_permitted()`: a public E1 kill gate (check and record the dispatch in one transaction, and have `stop()` wait for it), or a kill predicate evaluated inside C2 `execute`'s claim transaction.

- **The provenance boundary is incomplete.** Result provenance comes from the step's declaration plus an untyped `"provenance"` field in the result. Until typed results and ingress wiring exist (C8 / real connectors), a definition that wrongly declares a result trusted, or a builder that pulls tainted data in from outside `StepContext`, is not caught here. The rule is conservative: any callable builder inherits every earlier result's provenance, whether or not it reads those results.
- **Reconciled effects have no result.** C2's `reconcile` records a verdict, not the provider's response. After a crash, a step resolved by reconciliation passes `None` to later steps, and its provenance falls back to `unverified_result`. That fails closed: a dependent write needs an approval, or fails to bind.

- **Upgrading from `e2.v0`/`e2.v1` (to `e2.v3`) reconciles legacy approvals or holds them.** In the upgrade transaction, each live task's approval step gets a claim on its one existing E1 request only if exactly one exists and it is pending or approved. If none exists and the task is waiting on that step, no prompt was ever sent (E1 writes request and prompt together), so the first is issued normally. Everything else is **held**: several requests, a single terminal one, a pre-hash checkpoint reference, or none for a non-waiting step. A held task is parked in `waiting_approval`, never prompted again and never resumed from a guessed approval. Josh gets one `hold:` alert through the ops job, and an operator decides with `resolve_hold(task, approval_id)` (claim that exact request) or `resolve_hold(task, None)` (end the run). The whole upgrade is one transaction, so an interrupted upgrade leaves the old version and no partial claims. Old E2 code refuses the upgraded file, but a process already running old code cannot be fenced from here: **stop every old runner before upgrading.** Evidence uses databases produced by the actual prior code (`tests/legacy/`).
- **Read-only SQL on C3's `outbox`** to verify a long-work final exists before marking it delivered. No E1 API answers "is this notification enqueued?". Candidate follow-up: `LongWork.finished()` or an outbox lookup on `JobHandle`.
- **C2 additions in this PR** (cross-package; for the C2 owner): `TaskStore.release()`, and `tx=` on `submit()` and `complete()` so they can join the caller's write transaction (the same pattern as C3 `Outbox.enqueue(tx)`).
- **Interrupt is a pause, via a small C2 addition.** An interrupted run is handed back with `TaskStore.release()`, added to C2 in this PR. It is lease-checked in the write transaction, moves `running → queued`, and touches no failure counter. Repeated stops therefore never escalate a task, and a result held back by the kill flag is delivered after the flag clears. This is a cross-package change to C2 (T10) for its owner to review.
- **Approval cancelled by `/stop` → run fails.** E1 cancels pending approvals on `/stop`, and `poll_approvals` maps `cancelled` to a C2 denial (`failed`). Re-requesting after the flag is cleared would need a definition-level policy.
- **Direct reads of other packages' tables.** The runner reads, never writes, three things directly: E1's `approval_requests` (E1 has no API that returns the issued record, or the pending request for a task and action hash), and C2's `tasks` for `waiting_approval` and `escalated` ids and `jobs` for `escalated_at` (C2 has no list-by-state API). Candidate follow-ups: `ApprovalIssuer.record(id)`, `TaskStore.list(state=)`.
- **Claim has no kind filter.** The runner assumes it owns the task store's queue. A task whose kind is not one of its definitions is failed closed, not skipped.
- **`LONG_WORK_ACK_S`** is mirrored (30 s) because lint forbids importing `notifier.service` outside E1.
- **No real scheduler daemon or connectors.** `tick`, `run_pending`, `poll_approvals` and `watchdog` are called by the future C8 loop.

Evidence: `tests/test_responsibilities.py`, with fixtures in `tests/resp_world.py`. The restart tests SIGKILL a spawned worker mid-dispatch.
